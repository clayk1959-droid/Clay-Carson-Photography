Carson & Muller Family Photos

Site guide — how to run it, maintain it, and what's changed over time.

The site blocks search engines and well-behaved crawlers (robots.txt, noindex meta tags, and an X-Robots-Tag header on every response) so it won't show up in search results or get indexed. It's still reachable by anyone with the direct link — this isn't password-protected.

Any gallery can be marked private from the editor (request → approve → login, for sharing sensitive photos with specific people only). A private gallery stays visible in the public Galleries list with no lock icon, but requires a granted account to view — see Private Access Guide.md / .html for how the request/approval flow works and how to grant access from the admin page.

Your regular workflow (no coding required)

Everything here is a normal Terminal command or something you do in the browser — none of it needs Claude. The loop is always the same:

  1. Add or remove photos in Gallery Originals — drop a new folder in for a new collection, drop photos into an existing folder, or delete a folder entirely to take that collection down.
  2. Run npm run gallery:sync to rebuild the site from whatever's currently in Gallery Originals.
  3. Run npm run dev and check it at http://localhost:3000 — this also turns on the pencil-icon editor (fix a caption/date/order, hide a photo, move it to another collection, or set it as the collection's cover photo).
  4. Run npm run save — it asks what changed, records it, commits, and offers to push live.

That's the whole cycle. Reach for Claude for anything outside it: bugs, design/layout changes, or new features.

Local development

Requires Node.js 20 or newer.

npm install
npm run dev

Then open http://localhost:3000.

Adding or updating galleries

The gallery:sync script reads full-resolution originals, resamples them into a full-view size and a thumbnail size, pulls each photo's caption, person tags, and event tag from IPTC metadata (falling back to the creation date and filename when a photo isn't tagged), regenerates each gallery page, and regenerates the Collections index page — all automatically.

Resizing and metadata extraction are cached per photo (never committed to git) and skipped whenever a photo hasn't changed since the last sync — only new or edited photos actually get reprocessed. A sync where nothing changed finishes in a few seconds regardless of collection size; only touching/re-saving a source file (or adding/removing one) forces that photo to be reprocessed.

Adding photos to an existing collection

(e.g. more Norway photos):

  1. Drop the new photos into Gallery Originals/Norway (or whichever collection folder).
  2. Run npm run gallery:sync.
  3. Check it locally (npm run dev), then commit and redeploy.

Adding a brand-new collection

Just drop a folder in — no code editing or extra commands required:

  1. Create a new folder inside Gallery Originals and name it whatever you want the collection to be called (e.g. Gallery Originals/Beach 2026).
  2. Copy your photos into it. An empty folder is ignored — it won't show up as a collection until it actually has photos in it.
  3. Run npm run gallery:sync. It notices the new, non-empty folder, registers it as a collection (using the folder name as the title), creates its gallery page, and adds its card to the Collections index — all automatically.
  4. Check it locally, then commit and redeploy.

Removing a collection

Delete its folder from Gallery Originals entirely (not just its photos), then run npm run gallery:sync. It notices the folder is gone, takes down that collection's page and images, and drops it from the Collections index — all automatically, the same way adding a folder registers one.

If a folder's photos are tagged in Photo Mechanic (Person, Event, Alt Text), that data powers the caption and the Person/Event filters on the Collections page. Untagged photos still work fine — they just fall back to the photo's creation date and a cleaned-up version of the filename as the caption, and don't contribute a Person/Event tag.

npm run collection:add is still there as an optional shortcut if you'd rather create the empty folder (with a name you type at a prompt) before you've copied any photos in — it does step 1 for you. It's never required.

Choosing a collection's cover photo

The photo shown on a collection's card on the Collections page defaults to the first visible photo, centered, unless you set one. Two ways to do it:

  • In the browser (easiest): while running npm run dev, open the pencil icon on any photo and use the "Use this photo as the collection's cover" grid — clicking a direction updates a live preview so you can see how it's cropped to fit the card's box before committing (e.g. "left" if the subject sits on the left of the photo), then click "Set as collection cover".
  • In Terminal: run npm run collection:cover, pick the collection, type the photo's filename (it opens that collection's photos in Finder so you can find it), then pick a crop direction.

Either way, run npm run gallery:sync afterward to apply it.

Note: the sync script currently checks a hardcoded path (/Volumes/Samsung_T5/Website) for higher-priority metadata before falling back to the Gallery Originals copy. If that drive isn't present, it just falls back automatically — no changes needed unless that path changes.

Editing captions, dates, order, and photos locally

While running npm run dev, a small pencil icon appears in the corner of each thumbnail (hover to see it) and in the full-size lightbox view — click it to edit that photo's caption, date, or position within the collection, move it to a different collection, or delete it from the site entirely. This icon only exists when the site is running locally; it never appears on the deployed site, since it's gated on the server side (not just hidden with CSS).

Saving writes to a local overrides file — it never touches Gallery Originals or a photo's embedded metadata, and "Delete" only hides a photo from the site rather than removing the original file. To actually apply saved edits to the site, click the Sync Gallery button in the bottom-right corner (also local-only) once you're done editing — it runs gallery:sync for you, so there's no need to switch to a terminal. It's worth batching several edits before clicking it, since a sync reprocesses every changed photo's images. Either way, check the result locally, then commit and redeploy as usual — the overrides file is tracked in git, so edits survive future syncs and deploy along with everything else.

To reorder a bunch of photos at once instead of one at a time, click Reorder Photos next to Sync Gallery — it opens every visible photo in the collection as small thumbnails, all on screen together. Drag one anywhere and the rest reflow live, like arranging slides on a light table. Click Save order when it looks right, then Sync Gallery to apply it.

Changing the homepage hero photos

The homepage hero rotates through 4–5 photos, fading from one to the next. It uses two separate sets — one crop for desktop/iPad, one for phones — so each looks properly framed on its own screen:

  • public/homepage/desktop/ — wide crop, shown on desktop and iPad
  • public/homepage/mobile/ — portrait crop, shown on phones

To add, remove, or replace a rotating photo: export it from Photoshop (see the README file inside each folder for the exact crop and size to use) straight into the matching folder, using whatever filename you like. No sync command needed — the site picks up whatever's in those two folders automatically. Check it with npm run dev, then commit and redeploy as usual (npm run save).

Deploying to Vercel

The easiest path, since this is a standard Next.js app:

Option A — Vercel dashboard (no command line needed)

  1. Push this project to a GitHub repository (or upload it directly in the Vercel dashboard).
  2. Go to vercel.com, sign in, click "Add New Project," and import the repo.
  3. Vercel auto-detects Next.js — click Deploy. No configuration needed.
  4. Every future push to the repo auto-deploys.

Option B — Vercel CLI

npm install -g vercel
vercel login
vercel        # deploys a preview
vercel --prod # promotes to production

Custom domain

Once deployed, add your domain under the project's Settings → Domains in the Vercel dashboard, and update your domain registrar's DNS records as Vercel instructs (usually a single CNAME or A record). Propagation is typically minutes to a few hours.

Architecture & external services

What this site actually depends on outside its own code, and how much work it'd take to repurpose this for a different site (a friend's art gallery, say) — confirmed by checking the actual code and dependencies, not assumed.

Always required, as currently built

  • GitHub — the source of truth. A push to main is what triggers every deploy.
  • Vercel — hosting, split across three separate projects that all deploy from this one repo: the public site, the password-gated private-access/admin system, and the remote editor.
  • Google Fonts (fonts.googleapis.com) — loaded live by every visitor's browser for the site's typefaces. Free, but a real external dependency — the site isn't fully self-contained.

Only required if you use the feature that needs it

  • Resend (email) — only touched by private-gallery request/approval emails and the sync/deploy alert emails. A site with no private galleries and no alerting needs no email service at all.
  • Neon Postgres — only touched by the private-gallery system (accounts, sessions, access grants). Fully public galleries never open a database connection.
  • A GitHub Personal Access Token (separate from GitHub hosting the repo) — only used by the remote editor project, so someone without local file access can edit captions/tags from a browser. Skip the editor project, skip this token.
  • Vercel Blob (temporary photo-submission storage) — only touched by the "Submit Photos" flow, granted per-account and separate from private-gallery access. Files sit there just long enough to be reviewed — npm run submissions:pull downloads them locally and deletes them from Blob storage in the same step, so nothing accumulates there and there's nothing to pay for on the free tier.

Present but unused

Tailwind CSS is wired into package.json / postcss.config.mjs but nothing in the code actually references it — a leftover from the original project template. Safe to remove if repurposing this codebase.

Repurposing this for a different site

The core mechanism — drop images in a folder, run a sync script, get generated gallery pages with captions/tags, optional password-gated editing — isn't tied to photography or family content anywhere structurally. What genuinely isn't a cosmetic change:

  • About 9 hardcoded strings — the owner's email address, the mail.carsonmullerfamily.com sending domain, and "Carson & Muller Family" branding are literal text in several files (lib/private-access.ts, lib/editor-users.ts, the deploy-webhook route, the sync script, email subject lines, page titles) — not driven by one central setting. Real find-and-replace work, not a config flip.
  • Fresh accounts across the board — a new GitHub repo, a new Vercel account (one project if skipping private galleries/editor, three for the full setup), a new domain with its own DNS/SPF/DKIM if sending mail from it, a new Neon database and Resend account if using the private/alerting features at all.
  • A real simplification option — a site with no password-gated albums and no browser-based remote editing can drop Postgres and Resend entirely and run on just GitHub + Vercel.

Any capable coding AI (or a developer) can do this work — nothing here is specific to Claude. Don't hand over the real data along with the code: data/photo-data/*.json, data/gallery-overrides.json, and Gallery Originals/ contain real names and photos, and .env.local has live credentials that should never be shared — start fresh accounts under the new owner regardless of who writes the code.

Saving and publishing changes

Once the site is on GitHub and Vercel, use this any time you've made a change — whether it's new photos, a text edit, or anything else:

npm run save

It will:

  1. Ask what changed (type one line per change, then leave a blank line to finish)
  2. Add a new numbered entry to the changelog with today's date
  3. Commit everything with that description
  4. Ask if you want to push to GitHub now — if yes, Vercel picks it up and deploys automatically within a minute or two

If you're not ready to go live yet, answer "n" when it asks about pushing — your changes are still saved locally, and you can push later with git push.

If you ever need to roll back to an earlier version, the Vercel dashboard shows every past deployment with a one-click "Promote to Production" (i.e. rollback) button — no manual bookkeeping required.
